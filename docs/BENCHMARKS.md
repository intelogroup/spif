# SPIF Performance Benchmarks

This report details the execution speed of the **Semantic Provenance Inference Format (SPIF)** reference Python implementation (`spif`) across various document complexity levels.

This document contains both the serialization benchmark and the provenance /
attestation comparison. The latter is the relevant benchmark for SPIF's core
claim: attaching a verifiable, tamper-evident record of how an AI output was
produced, inline and per output.

The provenance comparison is generated by
[`benchmarks/provenance_comparison_bench.py`](benchmarks/provenance_comparison_bench.py).
Run it from the repository root with:
`python3 benchmarks/provenance_comparison_bench.py --reps 200`.
The benchmark prints its output to stdout. Save the output under
`spif-py/results/` manually if needed; that directory is gitignored;
regenerate it locally rather than committing result files.

## Architectural Performance Analysis

### 1. SPIF Integrity & Correctness Costs
* **Integrity Enforcement**: Unlike JSON, CBOR, and MessagePack which only deserialize structural bytes, **SPIF decode performs mandatory SHA-256 checksum verification** over the entire document body. This prevents corruption and unauthorized tampering at the ingestion site.
* **Topological DAG Safety**: SPIF decode validates that the node payload references and trace dependencies contain no cyclic loops ($O(N)$ fast-path validation), neutralizing recursive stack-overflow and Denial-of-Service vectors.
* **CBOR Custom Tags**: SPIF wraps specific fields (such as `Distribution`, `NodeRef`, and `Embedding`) in native CBOR tags (tags 1000–1002) for full cross-language serialization fidelity.

### 2. Microsecond-Level Latency
Even with full cryptographic validation, SPIF operations execute in **tens of microseconds**. This fits comfortably within the strict SLAs of real-time firewalls (e.g. Palo Alto Networks NGFW), API gateways, and client sidecar proxies.

### 3. Native Engine (Rust) Throughput
For high-throughput requirements, the native Rust library (`spif-rust`) achieves over **450,000 decodes/sec per core**, leveraging SSE/AVX vector instructions for hardware-accelerated signature checks.

## Provenance Comparison: SPIF vs. in-toto, C2PA, and Sigstore

The serialization table above compares encoding formats. This section compares
SPIF with systems that address provenance or attestation directly, including
where a comparison is not fair to make.

Quantitative numbers use the same single AI-response record for each measured
system. SPIF and in-toto are measured locally on equal terms: local keypair,
no network, and both signed. Latest rerun: Apple M2, Python 3.12.13,
`securesystemslib` 1.4.0, 2026-08-12, Reps=200, median of 3 runs.

```text
System                                    Build p50   Build p99  Verify p50  Verify p99   Size B
SPIF (signed, ed25519)                      113.0μ      131.3μ      170.5μ      186.6μ       828
in-toto (DSSE, local Ed25519 key)            76.6μ       91.5μ      151.8μ      181.8μ       896
```

Once both sides actually sign, **in-toto is ~1.5x faster to build** (76.6μs
vs 113.0μs), and SPIF is **~12% slower to verify** (170.5μs vs 151.8μs). SPIF is ~8%
smaller (828B vs 896B). The prior claim that SPIF
was several times faster was an artifact of comparing signed in-toto with
unsigned SPIF. SPIF's crypto-layer advantages are size and streaming decode;
unsigned SPIF remains available for callers who do not need per-record
non-repudiation.

**Sigstore** was not measured in the latest rerun. Its keyless workflow
requires network access to Fulcio, a fresh OIDC token, and usually a Rekor
transparency-log interaction. A local CPU microbenchmark would not represent
that workflow; any Sigstore latency figure should come from a separately
committed and reproducible live-infrastructure harness.

**C2PA** was not measured quantitatively because the native library rejects
the self-signed test certificate. C2PA requires a CA-chain-issued certificate
or configured trust-anchor bundle before producing a signed manifest. This
limitation was verified by direct API testing, and independently
cross-checked with `c2patool` (the reference Rust CLI, a separate binary from
`c2pa-python`): pointing it at the same self-signed cert via
`C2PATOOL_ALLOWED_LIST` still fails with "the certificate is invalid" —
`--allowed_list` alone isn't sufficient to admit it, confirming the
CA-chain requirement isn't a `c2pa-python`-specific quirk.

### Feature / Guarantee Matrix

| | SPIF | in-toto | C2PA | Sigstore |
|---|---|---|---|---|
| **Designed for** | Per-call AI output provenance | Software supply-chain build steps | Media content credentials | Keyless code-signing artifacts |
| **Trust model** | Bring-your-own key (or unsigned) | Bring-your-own key + layout policy | CA-chain-issued cert or trust anchor required | Ephemeral Fulcio cert bound to OIDC identity |
| **Network dependency to sign** | None | None | None once a cert is available | Fulcio and usually Rekor |
| **Transparency log** | No | No | No | Yes — public Rekor log |
| **Granularity** | Per-node / per-tool-call | Per build step | Per asset/file | Per artifact |
| **Streaming-friendly** | Yes — chunked CBOR | No — whole statement | No — whole asset | No — whole artifact |
| **Tamper detection** | Full document body; checksum and optional signature | Full DSSE payload | Full asset and manifest | Full artifact |
| **Confidence metadata** | Native `Distribution` type | No | No | No |
| **Best fit** | Streaming AI output and audit trails | Multi-step build pipelines | Media authenticity chains | Public software provenance |

### Where SPIF Has No Real Answer

- **No transparency log.** SPIF proves integrity and, when signed, signer
  identity, but has no public third-party-auditable log like Rekor.
- **No policy/layout language.** in-toto can enforce an authorized ordered
  multi-party build layout; SPIF has no equivalent policy mechanism.
- **Not a media-authenticity format.** C2PA is purpose-built for photo,
  video, and audio provenance and is not interchangeable with SPIF.

### Honest Positioning

SPIF's case is sub-millisecond, sub-kilobyte, zero-network provenance that can
be attached to every AI output or tool call inline, with confidence metadata
in the same envelope. It gives up the public transparency log, policy/layout
language, and CA-backed identity that make Sigstore, in-toto, and C2PA useful
in their respective domains.

## Rust verification snapshot

The Rust implementation has also been validated independently of the Python
microbenchmarks: 25 `cargo test` cases passed, 5/5 RFC 8032 Ed25519 vectors
and 150/150 Wycheproof vectors passed, and the tamper/truncation sweep rejected
15,664/15,664 bit mutations and 1,957/1,957 truncation points without a panic.
These are verification results, not a replacement for the signed provenance
comparison above.
